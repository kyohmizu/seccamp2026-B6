# 演習11: Cloud Deploy による承認付きデプロイの構築

「コンテナイメージの push を契機に Cloud Build が自動デプロイする」現在の構成を、Cloud Deploy を用いたリリース管理構成へと移行します。本番環境への反映前に手動の承認プロセスを配置し、障害発生時には過去のリリースへロールバックできる状態を構築します。ビルドの成功が自動で本番反映に直結しないよう、職務分掌の原則をデプロイ段階で実装します。

- 現在のデプロイ処理は、`src/pipelines/cloudbuild.deploy.yaml` から `gcloud run services update` を実行する構成になっています。本演習では、このデプロイ経路を Cloud Deploy に差し替えます。
- 既存のデプロイ用 SA（`<prefix>-deploy-sa`）には、あらかじめ `roles/run.developer`、Artifact Registry の閲覧権限、およびランタイム SA に対する `actAs` 権限が付与されています。本演習では、この SA を Cloud Deploy の実行サービスアカウントとして再利用します。
- 演習05（provenance ＋ Binary Authorization）までを完了した状態でパイプラインを構築している場合、承認されたデプロイ処理が Binary Authorization の検証を正常に通過することまで確認できます。なお、Cloud Deploy 単体の動作検証は演習05 の事前構築なしでも実施可能です。

## 課題
1. Cloud Deploy API を有効化し、デプロイ用 SA に実行に必要なロール（`roles/clouddeploy.jobRunner`）を追加してください。
2. デリバリーパイプラインおよびターゲット定義（`prod`、`requireApproval: true`）を作成し、`gcloud deploy apply` コマンドで登録してください。ターゲットの実行サービスアカウントにはデプロイ用 SA を指定します。
3. frontend の最新イメージの digest を解決し、その digest を指定してリリースを作成してください。
4. ロールアウトのステータスが承認待ち（`PENDING_APPROVAL`）で停止することを確認してください。
5. ロールアウトを手動で承認し、Cloud Run に新しいリビジョンがデプロイ・反映されることを確認してください。
6. 過去のリリースへのロールバックを実行し、承認プロセスを経て以前のリビジョンへ安全に復元できることを確認してください。
7. Cloud Build の自動デプロイトリガーを無効化（停止）し、デプロイ経路を Cloud Deploy へ一本化してください。

<details>
<summary>ヒント</summary>

- ターゲット設定の `requireApproval: true` が承認ゲートとして機能します。ロールバック実行時も該当ターゲットに対する新規ロールアウトとして扱われるため、同様に承認が必要となります。
- コンテナイメージはリリース作成時に `--images` フラグを用いて digest 参照へ差し替えます。マニフェスト（`run-service.yaml` 等）側には、プレースホルダーとしてのイメージ名（`frontend`）を記述しておきます。
- Cloud Run のサービス名およびランタイム SA（`<prefix>-frontend`、`<prefix>-frontend-sa`）は既存のリソース名と一致させてください。異なる名前を指定した場合、新規サービスとして作成されてしまいます。
- Cloud Deploy はマニフェストの `spec` 定義に基づいて Cloud Run サービス全体を完全置換します。現在稼働中のサービスに設定されている環境変数（`BACKEND_URL`）、Ingress、ポート等の設定を `run-service.yaml` へ漏れなく定義してください。設定が欠落している場合、新リビジョンへの更新時にそれらの設定が失われます。
- リリース作成直後のロールアウト状態は `PENDING_RELEASE` であり、処理が進行すると `PENDING_APPROVAL`（内部状態: `NEEDS_APPROVAL`）へ遷移します。ステータスが承認可能状態へ変化する前に `approve` コマンドを実行すると 400エラーが発生するため、状態遷移を確認した上で承認操作を行ってください。
- 使用している `gcloud` CLI のバージョンによってサブコマンドやフラグの名称が異なる場合があります。必要に応じて `gcloud deploy --help` でコマンド仕様を確認してください。

## 検証
- リリース作成後、承認前の状態では変更が反映されず、承認操作を行って初めて Cloud Run のリビジョンが切り替わることを確認してください。
- ロールバック処理により過去のリリースの設定に基づいて新しいロールアウトが作成され、承認手順を経て以前のリビジョンへ復元されることを確認してください。
- Binary Authorization を有効化している環境では、承認後のデプロイ処理であっても未検証イメージが確実に拒否されることを確認してください（デプロイの実行主体を変更しても、Cloud Run 側の検証メカニズムは正常に適用されます）。

## 発展
- ターゲットを `staging` と `prod` の2段階構成にし、`staging` 環境へのデプロイは自動化しつつ、`prod` 環境への昇格（プロモーション）には手動承認を必須とするパイプラインへ拡張します。
- リリース作成処理を Cloud Build のビルド後ステップに組み込み、「ビルドおよびリリースの作成は自動、本番環境への適用は手動承認」という役割分担（職務分掌）を構成します。
- Cloud Deploy のデプロイフック（Pre-deploy hooks）を活用し、デプロイ直前に `cosign verify` や `slsa-verifier` による検証処理を実行する構成を追加します（演習06 との連携）。
