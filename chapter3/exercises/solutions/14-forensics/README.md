# 解答: 攻撃デモのフォレンジック

この演習の主眼は、**防御側が実際に取得できる証跡だけで、攻撃をどこまで追えるか**です。デモ用に仕込んだ痕跡（マーカーファイル・警告表示）や攻撃者側の C2 受信ログは、実際の攻撃では使えません。防御側が頼れるのは、パイプラインのログ・ネットワークの通信記録・ランタイム監視です。

## 悪性コードの挙動（静的解析の結論）

| タイミング | 通信 |
| --- | --- |
| インストール時（postinstall） | メタデータサーバ（169.254.169.254）へ GET、C2 へ POST |
| 実行時（formatYen 呼び出しごと） | メタデータサーバへ GET、C2 へ POST |

## 防御側が使える証跡と、その見え方

| 証跡 | 取得方法 | 見えるもの | 見えないもの |
| --- | --- | --- | --- |
| パイプラインのログ | Cloud Build のビルドログ（`--foreground-scripts` 等） | インストール中のスクリプト実行の痕跡 | 攻撃者が出力を抑制すれば痕跡は残らない |
| ネットワークの通信記録 | VPC Flow Logs / Cloud NAT ログ | 外部 C2 への通信（宛先・タイミング・通信量） | 送信データの中身（暗号化なら宛先のみ）。メタデータアクセスは記録されない |
| ランタイム監視 | eBPF（Falco / Harden-Runner 等） | プロセス起動、メタデータアクセス、外向き接続 | 導入していなければ何も残らない |

## 重要なポイント

- **メタデータサーバ（169.254.169.254）へのアクセスはネットワークログに出ない**。リンクローカルアドレスで、通常のネットワークを経由しないため。これを捉えるにはランタイム監視（プロセス／システムコールレベル）が必要。
- **送信データの中身は、防御側の通信記録からは基本的に分からない**。分かるのは「いつ・どこへ・どれだけ」。中身まで見えるのは攻撃者側（C2 受信ログ）の視点。
- **事前にログ・監視を仕込んでいなければ、事後に追える情報は限られる**。フォレンジックの成否は、攻撃前にどれだけ証跡を残す設定をしていたかで決まる。

## 手順（例）

```bash
# パイプラインのログ
gcloud builds list --limit 5
gcloud builds log <BUILD_ID>   # install ステップに postinstall の痕跡がないか

# ネットワークの通信記録（GCP）
#  1) 対象サブネットで VPC Flow Logs を有効化
#  2) Cloud NAT を使う構成なら NAT logging を有効化
#  3) Logs Explorer で外向き通信（未知の宛先・:9099 等）を検索

# ランタイム監視
#  GKE / VM: Falco 等で execve・connect を監視し、169.254.169.254 や外部への接続を検知
#  CI ランナー: StepSecurity Harden-Runner 等で egress とプロセスをベースライン化

# ローカルでの通信観察（補助。メタデータには到達しない）
cd src/demos/malicious-dependency
local/up.sh
sudo tcpdump -nn 'tcp port 9099'
```

## デモ痕跡について（実運用では使えない情報）

- マーカーファイル（`flowpay-demo-PWNED-install.json`）と警告表示は、デモを分かりやすくするために仕込んだもの。実際の攻撃者はこうした目立つ痕跡を残さない。
- C2 受信ログ（mock-attacker / attacker-receiver）は攻撃者側の記録で、防御側からは見えない。
- これらは「攻撃が実際に何をしたか」という正解の確認に使い、防御側の証跡（フローログ・ランタイム監視）でどこまで同じ全体像に迫れるかを比較する材料とする。
