# 演習03: 依存パッケージの固定（lockfile ＋ npm ci）

前演習における digest 固定はベースイメージに対する制御手法でした。同じ「ビルド入力を決定論的に固定する」原則を、アプリケーションの依存パッケージにも適用します。frontend では `package-lock.json`（lockfile）を Git リポジトリにコミット済みですが、初期状態のパイプラインの `frontend-deps` ステップでは `npm install` を使用して依存関係を導入しています。`npm install` は `package.json` と lockfile の間に不整合（ドリフト）が存在する場合、警告なしに依存関係を再解決して lockfile を自動書き換えしてしまうため、事前レビューを経た lockfile の定義どおりに導入される保証が得られません。

## 関連
- 2-2「マルウェア・悪性依存対策」（依存関係の完全固定）
- 1-1 Shai-Hulud / axios。悪性パッケージの混入事例であり、その多くは**推移的依存関係**（Transitive dependencies）の経路を経由して導入されます。

## npm install と npm ci の違い
- `package.json` に記述された `^1.0.0` などのバージョン指定は「1系の最新バージョン」の適用を許容するため、依存更新（`npm update` 等）を実行した時点でインストール結果が変化する可能性があります。
- **`npm install`**: lockfile が存在する場合はその定義を参照しますが、`package.json` との間でドリフトが生じている場合は警告なく自動調整を行って lockfile を書き換えます。そのため、CI 環境でインストールされるコンテンツがレビュー済みの lockfile と一致する保証が得られません。
- **`npm ci`**: lockfile に記録された定義に完全一致する依存パッケージのみをインストールし、`package.json` との間に不整合があれば処理を失敗させます。さらに、integrity（ハッシュ値）によるコンテンツ検証も同時に実施します。これは、コンテナイメージにおける digest 固定に相当する依存パッケージ側の完全固定手法です。推移的依存関係の完全固定とハッシュ検証までを担保できるのは、lockfile ＋ `npm ci` の組み合わせのみです。

## 課題
1. パイプライン定義の `frontend-deps` ステップ（`pipelines/cloudbuild.yaml` および PR チェック用トリガー定義ファイル）における実行コマンドを、`npm install` から `npm ci` に変更・修正してください。
2. lockfile と `package.json` が完全に整合した状態で、ビルドパイプラインが正常に成功することを確認してください。
3. （任意）`package.json` に記述されている直接依存パッケージのバージョン指定を、exact（キャレット等を外した完全固定）に変更してください。

## 本演習で防げること・防げないこと
- **防げること**: レビューを経ていない依存ツリーが CI 環境に混入するリスクの排除（ドリフトおよび不意の変更の検知）、ビルドの非再現性の解消。
- **防げないこと**: 依存パッケージの更新（`npm update` や Dependabot 等）の際、公開直後の悪性バージョンを lockfile 内に取り込んでしまうリスク。`npm ci` は取り込まれた lockfile の定義に従って忠実に構築を行う仕組みであり、更新時の混入自体を止めることはできません。このリスクに対しては、cooldown（`min-release-age`）の設定および lockfile の差分のレビューによって対処します（[cooldown-dependencies](./08-cooldown-dependencies.md)）。

## 検証
- ビルドログを確認し、`frontend-deps` ステップで `npm install` ではなく `npm ci` コマンドが実行されていることを確認してください。
- `package.json` または `package-lock.json` を意図的に変更して不整合（ドリフト）を生じさせ、`npm ci` が検知して適切に処理を失敗させることを確認してください。
